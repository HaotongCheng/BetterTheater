# 局内状态回放原型（可抛弃）

对应票：[用观测回放验证局内状态更新与回溯隔离](https://github.com/HaotongCheng/BetterTheater/issues/16)。
这是决策材料，不是产品架构。它回答的问题是：**怎样根据带来源的实际观测维护局内状态，使推荐未执行不改变事实、重复读取不重复入账、暂不可见不当作零值，并在失败或回溯后避免旧分支污染当前局面。**

## 运行

双击 `index.html`。单文件、无依赖、无网络、无持久化；关掉就清零。

页面自上而下：问题与提议的四个状态边界 → 九条更新契约 → 当前局面（逐字段带来源与新鲜度）→ 刚才发生了什么 → 自由操作（任意顺序点观测、建议、重复帧）→ 六个引导情景 → 观测账本。

## 输入是什么

- **人工标注观测**：S 批 23 张（2026-09-18，2560×1440）与 E1 批 13 张（2026-09-16/17 合作局，用户裁切图）的字段真值，取自 `prototypes/fixed-screenshot-reading/labels.py`（分支 `prototype/fixed-screenshot-reading`，用户 2026-09-30 复核）。角色用中性代号：S 批 P–W，E1 批 A–J。局前页与弹层按识别路线的结论记为“拒判”。
- **合成用例**：明确标紫色，只为示范流程（缺席、全灰、同幕回溯、重试计数）。合成用例里的数值不是游戏规则证据，尤其是回溯后恢复了什么。
- **建议**：四条合成建议，只进账本。

没有 OCR、没有真实捕获、不含任何截图。

## 文件结构

`index.html` 内有三段脚本：

1. `TheaterLedger`：纯状态模块，不碰 DOM。`observe` / `recommend` / `undo` 维护账本，`project` 把当前分支投影成局面并附跨分支的本局记录，`projectNaive` 是对照用的朴素快照。这段可以整体搬走。
2. 观测数据与情景定义。
3. 页面外壳：只调用模块与渲染。

控制台可用 `__replay(n)` 一次跑完第 n 个情景（0 起）。`scratch` 不入库。

## 已知边界

- 结算归属靠“最近一次开战前页面”，并用“之后看到事件页 / 伙伴选人 / 获得结果页即视为放弃开战”这一条 UI 流程推断来剪枝。这是本原型唯一的流程推断，须由用户确认是否符合实际操作路径。
- 两次结算只有在同结果、同用时、其间没有新的开战前页面或事件页时才合并；没有开战前页面且同用时的连续两场会被误合并。
- 身份未配对的列表（卡片式页面、E1 最后一战）只记人数与耐力分布，不更新逐人状态；这是识别侧的缺口，不是状态模型能补的。
- 不模拟圣牌完成状态、神秘收获触发与层数；只读“裂隙入口可见数”。
